# 設計メモ

なぜこの作りにしたか、後から読んで判断の理由が分かるように残しておく。

## 1. 基準日ドリブンにした理由

日付を1つずつ手で入力する方式は、**審査会が動いた瞬間に破綻する**。
そこで、保持するのは次の2つだけにした。

- **基準日**（審査会日など）＝ 回次ごとに1つ
- **相対日数の定義**（工程テンプレート）＝ 業務ごとに1セット

実際の日程はこの2つから毎回計算する。工程表シートは計算結果のキャッシュに近い。
結果として、審査会が1週間ずれても**基準日のセルを1つ直すだけ**で全工程が追随する。

### 工程間の連鎖を許した理由

「決裁が返ってくるのは起案からN営業日後」のように、実務の日程は**基準日ではなく前工程に紐づく**ものが多い。
基準日からの相対だけで表現すると、起案が1日ずれたときに後続を全部手で直すことになる。
そのため基準に「別の工程名」を指定できるようにし、依存を解決してから日付を確定させている（`computeSchedule`）。
循環参照は解決不能なので、保存時とプレビュー時にエラーとして弾く。

## 2. 個人情報を持たない設計

工程名と日付しか持たない。「11/12 封入封緘」は個人情報ではないので、
個人情報保護条例やクラウド利用の内規に関する説明の負担が大きく下がる。
テンプレートのJSONを人に渡せるのも、中身に個人情報がないからこそ成立している。

## 3. 権限を最小にした

要求するのは `spreadsheets` / `script.external_request` / `script.scriptapp` / `script.container.ui` の4つだけ。

- **祝日は内閣府の公開CSVから取得**する。Googleカレンダーから取る方法もあるが、
  それだとカレンダー権限が必須になる。一次情報である点でもCSVの方が良い。
- **通知は Chat Webhook（HTTP POST）**。Gmail送信権限が不要になる。
- **カレンダー同期は任意機能**として分離し、既定はOFF。使う人だけがスコープを足す。

権限が少ないほど、承認画面の説明も、組織への説明も楽になる。

## 4. 1人1コピーを前提にした

利用形態が「各自が自分のスケジュールを管理し、必要なら人に渡す」なので、
複数人での権限分離やロック制御は作っていない。代わりに次を重視した。

- コピー → ［初期セットアップ］1回で動く
- 業務定義をJSONで書き出し／読み込みできる
- トリガーは各自のアカウントで設置するため、異動によるトリガー停止の影響が自分の中で閉じる

## 5. 純粋関数と I/O の分離

営業日計算・基準日展開・工程算出・通知の振り分けは、GAS の API に触れない純粋関数として
`01`〜`04` に切り出した。これにより Node で実行でき、実際の祝日を使った検証ができる（`tests/run_tests.js`）。
GAS 上でしか動かせないコードにすると、営業日計算のような**間違えると全部ずれる部分**を検証できなくなる。

## 6. 再生成しても手入力を壊さないこと

`generateSchedules()` は工程表を毎回作り直すが、次は引き継ぐ。

- 状態・完了日・担当・備考（人が入れたもの）
- 「日程固定」がONの行の予定日（自動計算を意図的に上書きしたもの）
- テンプレートから消えた工程でも、進捗が入っていれば履歴として残す

「自動生成」と「手入力」が同居するツールでは、ここを雑にすると信用されなくなる。

## 7. 既知の割り切り

- **同時編集の競合制御はしていない**。1人利用前提のため。
- **祝日CSVが取れないとき**は既存の祝日行を残す。消してしまうと営業日計算が静かに狂うため、
  「取れなかった」とログに残して現状維持する方が安全と判断した。
- **回次のラベル**は月次なら `YYYY-MM`、年次なら `YYYY`。年度表記が必要なら業務マスタ側で読み替える。
- ガントの基準日変更は `prompt` での日付入力。カレンダーピッカーにする余地はある。

## 8. Apps Script が使えない環境への代替案（未実装・検討済み）

組織の管理コンソールで Apps Script が無効化されている場合に備えて、
単体HTMLファイル版の実現性を検証した。**現時点では未実装。**

### 保存はできる（Chromium で file:// を開いて実測）

```
isSecureContext     : true
localStorage        : OK
indexedDB           : 利用可
showSaveFilePicker  : function   ← File System Access API が使える
showOpenFilePicker  : function
download属性        : true
```

### 想定する構成

「JSONファイルが正、localStorage は作業キャッシュ」の二段構え。

1. 操作のたびに localStorage へ自動保存（操作ゼロで継続できる）
2. ［保存］で共有フォルダ上のJSONファイルへ書き出し、次回は同じファイルを開き直す
3. Chrome / Edge 以外では、書き出し・読み込みボタンで代替する

保存対象は業務マスタ・工程テンプレート・基準日・進捗のみで、実日程は毎回計算するため
数KBに収まる。この設計は Apps Script 版と共通で、コアの純粋関数もそのまま流用できる。

### この案の利点と弱点

利点は、Google に接続できない端末（LGWAN接続系）でも動き、共有フォルダに JSON を置けば
係内で共有できること。権限もネットワークも要らない。

弱点は次のとおり。

- File System Access API は Chrome / Edge のみ。他は書き出し・読み込みボタンでの運用になる
- `file://` の localStorage はローカルファイル全体で1つの領域を共有するため、
  複数の台帳を使うならキーの名前空間を分ける必要がある
- ブラウザの閲覧データ削除で localStorage は消える。だからJSONファイルを正とする
- 同時編集は後勝ちになる（1人1コピー前提なら問題にならない）
- **自動リマインドは作れない。** ブラウザを開かないと何も起きないため、
  カレンダーへのCSVインポートで補う想定。ここだけは Apps Script 版に明確に劣る
